The problem

In a haemorrhage, the first delay is finding the blood.

Stock is spread across many small banks. The context that should decide who gets scarce O-negative lives in free-text notes, which a stock spreadsheet cannot read.

1–6 hours

Obstetric providers in Bihar estimated they wait one to six hours to receive blood; at least two hours to get it from another medical college.

Global Health Action, 2019 ↗
30.9 min

Mean emergency issue time inside one bank, from request to blood leaving: 125 cases, Government Medical College Trivandrum.

Asian J. Transfusion Science 2015 (abstract) ↗
15% short

India's annual collection fell 15% below the WHO 1%-of-population norm, across 2,903 blood banks (March 2018).

Factly, 2018 ↗

How it works

The model judges. Code decides. An officer confirms.

Every number (stock now, stock after dispatch, units already pending, ABO/Rh compatibility) is computed in code and given to the model as fact.

  1. Read the requestGroup and units parsed from the note. Ambiguous means hold.Code
  2. Pull live stockEvery bank in the district from e-RaktKosh.Code
  3. JudgeUrgency, reserve safety, priority conflicts and substitution, with a probability for every answer.Decisions API
  4. Decide and rankThresholds from policy.yaml. Blocked banks stay visible with the reason.Code
  5. Explain and confirmGPT-6.1 Sol drafts the bank request and the officer's explanation. The officer confirms.Officer

Safety

Fails closed, every time.

  • Any error, refusal or malformed answer ends in HOLD_FOR_HUMAN, never RECOMMEND.
  • If the live stock fetch fails, nothing is recommended from the old snapshot.
  • Never empties a bank, and never leaves less than pending orders already need.
  • No automatic dispatch. Confirm writes to an audit log, with overrides flagged.
Built on OpenAI

Typed judgments, not chat.

  • Decisions API (gpt-6-luna): urgency score, reserve and priority choices, substitution and ambiguity predicates, with a probability per option that code can threshold.
  • GPT-6.1 Sol (Responses API): writes the bank request, the explanation and the follow-up question. It cannot change the decision.
Ready to use

Pilot-ready today.

  • Reads the Health Ministry's live e-RaktKosh API directly.
  • Works for any district e-RaktKosh covers. Set two codes; no code change.
  • Integrate through POST /route and POST /confirm, or the CLI.
Not yet

Honest limits.

  • Does not place orders in a bank's own system or move blood.
  • Fetches O-negative and O-positive only; other groups go to the officer.
  • Pending orders are synthetic; e-RaktKosh publishes stock, not reservations.
  • No sign-in yet. Not a medical device.
